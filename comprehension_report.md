**What this proposes**
This document proposes a JavaParser-based refactoring tool (`de.tk.refactoring.tool`) that automatically separates a target Java module's externally consumed API from its internal implementation classes to eliminate transitive module dependencies. Using a dependency metamodel (`ModuleMetamodel`—which for testing is generated by scanning `@Api` annotations via `ApiAnnotationScanner`), the tool leaves API-conformant classes (`isApiKonform = true`) in place, replaces non-API-conformant classes with API interfaces under their original fully qualified names (or updates existing API interfaces), and moves the implementation classes (`*Impl`), internal helper classes, and newly generated `*Intern` interfaces into an `impl` subpackage. To decouple object creation and static method calls without introducing compile-time dependencies from the API package to the `impl` package, the tool generates `*Provider` interfaces in the API package with static `ProviderHolder` injection points and corresponding `@ImplementationClass`-annotated `*ProviderImpl` classes in the `impl` package bound at runtime via a ClassGraph-based Google Guice module (`ClassGraphGuiceModule`), while syntactically rewriting constructor calls to `<ApiInterface>.create(...)` and wrapping internal method calls on API-typed references in `((<Name>Intern) scope)` casts based on recorded line numbers.

**How the existing system works, per this document**
In the existing Java codebase (represented in the test suite by target module `projectA` and caller module `projectB`), external modules directly reference concrete implementation classes of a target module to invoke instance methods, constructors, static methods, and `public static final` constants. Some implementation classes have no separate API interface at all, while others implement an incomplete API interface (such as `BillingService` implementing `BillingServiceApi`) and are still referenced directly by their concrete class type in API signatures and external callers. Because callers depend directly on concrete implementation classes that internally reference additional helper classes, inheritance hierarchies, and infrastructure types, dependent modules pull the entire transitive closure of the implementation layer into their compile and runtime classpaths.
